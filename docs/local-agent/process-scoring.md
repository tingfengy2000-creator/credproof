# 运行结果与 Agent 过程证据分别计分

本规则在真实 B/C/D 模型对比开始前登记；已有 A-only 隔离预检不用于调整模型评分。六例是开发可见合成案例。汇总程序只读 JSON 日志，不运行候选，不调用模型，不改判定器、协议或旧记录。代码补丁最终通过，不等于 Agent 已完成诊断、主动复现、修复与复验。

## 必须分开的四项结果

1. **产物验收**：沿用固定 judge 的最终 PASS/FAIL/UNKNOWN。四个原始泄露案例分别报告修复通过数 `/4`，两个正常案例报告最终通过数 `/2`；少跑的案例显式列缺失，不能换成完整六例口径。模型 ERROR/预算停止后留下的补丁可以单独记录产物 PASS，但不能据此记模型完整完成任务。
2. **诊断**：只有最终 JSON 的 `initially_leaking` 是严格布尔值且 `diagnosis` 非空，才有可评分诊断；缺失、字符串 `"false"`、未解析 JSON 单列未知。与预先标签比对。正常误报只指把正常案例诊断为泄露，不能把任意格式修改等同误报。A 固定变换没有独立诊断输出，因此诊断指标 N/A，不能用“有无修改”替代。
3. **主动复现**：仅统计 C 实际调用 `run_controlled_case`，目标为 `original`，模型自选结构化输入且返回 `CREDENTIAL_LEAK` 的记录。外层统一 initial preflight、最终完整矩阵以及 `verify_patch` 在隐藏矩阵中发现泄露，均不算模型主动构造了触发输入。错误类型 `RESPONSE_CONTRACT` 单独出现也不算复现凭据泄露。记录首次补丁前是否已复现。
4. **反馈后的修改**：区分“原始泄露反馈后提交首个补丁”与“已有补丁失败后再修改”。仅工具日志先后排列不够：模型可能在同一回复并列提出测试和补丁、尚未看见测试结果。汇总核对模型 call 序号、原生 tool-call ID 和下一次模型请求中的 tool 结果；只有反馈确实进入较晚模型请求，且后续补丁源码与该失败版本不同，才记为可观察反馈后修改。此事实不自动证明反馈导致改善。

## C 的机械条件与人工确认

泄露案例的机械条件：模型正常结束、存在正确类型的正诊断、真实读源码、第一次补丁前在原始版本上主动复现、假设非空、失败反馈实际进入后续模型请求、提交发生变化的补丁、模型主动验证最终提交版本得到 PASS、外层最终验收也 PASS。满足仅标 `MANUAL_REVIEW_REQUIRED`，不自动给出“Agent 成功”。未满足标 `NOT_ESTABLISHED`，保留具体事件供复核。

人工逐项核对以下内容，并引用 `result.json` 的 trace 序号和对应模型请求：

- 假设是否在执行前明确预测**哪个条件、哪个输出通道、何种泄露机制**，而不是空串、“测试一下”或事后改写。汇总仅检查非空，绝不自动判断语义质量。
- 实际输入是否检验该假设，观测通道是否与预测相符；如假设被否定，后续结论是否承认并调整。
- 修复理由是否解释了观测证据与改动的对应关系；只在反馈之后发生修改不构成“依据反馈修改”的充分证明。
- 若声称“失败后再修复”，是否真的存在**失败补丁**、后续模型读到失败、不同补丁和新的通过证据。首补丁即通过应记录“未发生再修复”，不能故意制造失败或把它算作能力缺失。
- 最后被验收的版本是否就是实际最后提交版本。当前控制器固定选择最后提交版本，不按模型 JSON 的 `final_candidate` 回溯择优；提示与报告应明确该规则。

正常案例无需编造泄露或修复。正常流程机械条件是模型正常结束、明确无泄露诊断、读取源码、主动验证原件 PASS，最后原件也通过。保留修改、误报、功能失败、语法/受限源码拒绝、无有效候选、UNKNOWN 五类不同结果；语义保持的额外改动不是功能改坏，但须报告不必要修改。

## 比较口径与限制

| 方法 | 案例 | 生成预算上限 | 可见执行反馈 | 最终判定 |
|---|---|---|---|---|
| A-fixed | 同六例 | 0 模型调用；一次固定变换 | 无模型 | 同一完整矩阵 |
| B-once | 同六例 | 1 × 2048 token | 无 | 同一完整矩阵 |
| C-agent | 同六例 | 至多 12 × 2048 token；至多 3 补丁 | 至多 12 次自选执行、4 次隐藏验证 | 最后提交版本，同一完整矩阵 |
| D-no-feedback | 预选 p01/p03 | 每例 3 个独立候选，各 1 × 8192 token | 候选之间无反馈 | 每份独立记录，同一完整矩阵 |

C 与 D 仅**配置的最大生成 token 合计**同为 24576；实际 token、提示长度、调用次数、时限和上下文增长不相同，不能称严格等计算量或单变量消融。D 的六份候选来自两个案例，不能当六个独立案例，也不能把事后 best-of-three 当一次修复成绩。B/C seed 0、D seed 1/2/3，模型/权重与其他采样参数保持一致并记录实际值；单次运行不证明稳定性。

首轮客户端的输入门限是保守 UTF-8 wire bytes，不是实测 tokenizer 数量。该门槛导致六个 C 提前停止，原始结果保留。第二轮仅在完全相同的已测请求前缀上使用服务端报告的 prompt token 数，并对新增消息保守预留；具体修改见 framework.md，不丢历史、不扩 16K，不改变本页评分条件。输出预算上限不保证可全部使用。报告模型实际 status、usage 缺失数、调用次数、总耗时和隔离次数；不要把 `elapsed_s`（含最终验证）称为纯推理时间。

全部方法反复使用同一固定矩阵。C 可在过程中得到最多四轮该矩阵的聚合反馈，因此最终验收不是独立未见测试集。可支持这批受控任务的闭环演示，不能据此声称泛化、安全完备性或反馈的因果优势。A 已在这批案例修复 4/4、保留正常 2/2，不能通过降低基线来制造 Agent 优势。

## 汇总方式

运行 `python -m agent_pilot.summarize --records <已有完整运行目录> --output <新的目录>`。输出 `summary.json`、`cases.csv`、`summary.md`。程序校验预注册 manifest 与运行冻结哈希一致，拒绝覆盖目录或向原记录内部写入；缺少的模型方法不生成零分或虚构成绩。JSON 保留可核查假设、触发输入、修复理由及反馈送达证据。人工确认结论应另行记录审阅者和理由，不能改写原始运行。
