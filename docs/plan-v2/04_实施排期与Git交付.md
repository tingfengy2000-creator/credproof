# 实施排期、Git 管理与答辩交付

本文件是待评审的实施计划。14 天按单个主项目估算，实际进度取决于功能验收和返工；不是完成或获奖保证。

## 1. 分工与时间使用

| 角色 | 主要工作 | 每阶段必须参与的事项 |
|---|---|---|
| Codex | 前后端实现、合成样例、自动验证、实验脚本、结果汇总、Git 提交与问题修正 | 给出可运行产物、验证证据和具体限制，不能用截图代替真实后端结果 |
| 你 | 产品方向、核心设计判断、样例合法性确认、现场验收和答辩理解 | 每天 4—5 小时，优先检查主线而非逐行手写代码 |
| 队友 | 作品说明书、图表整理、PPT、演示脚本、格式核验 | 从真实版本提取材料，确保图片、功能、实验数字一致 |

工程投入建议约 40% 用于前端与交互，30% 用于核心后端，20% 用于实验和集成，10% 用于交付整理；这是分配建议，不是固定工时计费。队友的文档工作从第 2 天并行开始，不能把论文式包装留到最后一天。

用户学习负担重点放在五个概念：工作区/index 的区别；快照与副本；PASS/FAIL/UNKNOWN；模型只解释证据；“副本通过”不等于“原密钥已撤销”。无须先学完整的 React、训练框架或分布式系统。

14 天里优先完成 P0。第 8 天仍无法跑通真实副本修复时，取消 P1，保留已做好的前端质量和核心实验。第 9 天模型资源不满足时，可人工选择已取得的 0.6B 做单独验收，运行时不自动下载或切换；若解释仍不可靠，保留模板降级并如实记录，不拿未经核验的生成结果凑亮点。

仅模板可用时应写“核心闭环可运行，模型路径尚未完成或已停用”，不能说包含模型要求的全部 P0 已通过。模型接口至少一次真实生成和全部降级路径都经过验证后，才记录该项完成。

P1 只有在 P0 闭环和核心反例验收通过后才进入：先有限历史，再对象关系，最后扩大样本。不能为了展示历史扫描而删掉验证失败处理。

## 3. 每一阶段交付什么

| 阶段 | 可检查产物 | 需要通过的检查 | 进入下一阶段的依据 |
|---|---|---|---|
| A：界面骨架 | 页面、组件、类型契约 | 桌面/窄屏布局、导航、加载/空/错误状态 | 你认可界面方向，接口结构稳定 |
| B：真实发现 | 采集器、候选和证据记录 | 原仓库只读、位置正确、skip 可见、脱敏 | 页面可以追溯每条真实结果 |
| C：可验证修复 | 计划、副本、义务结果、报告 | 成功和失败反例；源变动；索引残留；缺少功能证据 | 无未解决的错误通过案例 |
| D：模型与实验 | 模型适配、回退、冻结结果 | 引用/隐私/越权结论和真实测时 | 可说明增益与限制，关闭模型仍可演示 |
| E：交付 | 版本、启动说明、录像和材料 | 干净环境主线、内容一致性 | 你完成最终走读 |

单次报告需要列出“本次改动、最小验证、仍未支持什么、对应提交”。低影响的纯视觉改动以浏览器走读为主；状态判定、读取范围和凭据处理必须有针对性的自动检查。

## 4. 推荐的正式目录结构

以下是评审通过后的目标结构。当前仓库只创建了设计目录，不表示这些业务目录已经存在。

```text
credproof/
  frontend/                # React / TypeScript / Vite
    src/
      app/                 # 路由、布局、主题
      components/          # 标签、列表、时间线、差异视图
      features/            # overview evidence repair assistant reports
      api/                 # typed client，统一错误和轮询
      types/               # 展示对象契约
  backend/
    app/
      api.py               # 本地会话、范围、任务、报告入口
      jobs.py              # 单任务调度与用例编排
      sources.py           # worktree / index / 可选 history
      scan.py              # 规则、候选和脱敏
      repair.py            # 白名单变换与副本
      verify.py            # 固定义务及三态结论
      assistant.py         # Ollama 适配与输出校验
      store.py             # SQLite、私有任务目录索引
      report.py            # 脱敏报告
  tests/
    fixtures/              # 明确合成、不能用于登录的测试材料
    contracts/             # 来源、范围、义务和接口检查
    integration/           # 自有仓库端到端验证
  experiments/             # 开发/留出划分、评估脚本、公开脱敏结果
  docs/plan-v2/             # 本次方案与原型
  scripts/                 # 启动、检查、演示辅助
```

运行数据放到仓库之外的用户指定本地目录，包含快照、完整差异和临时副本；模型缓存由 Ollama 管理。Git 中只保留源码、脱敏结果、合成样例和必要设计资源。

## 5. Git 管理约定

仓库：`tingfengy2000-creator/credproof`，私有。2026-09-28 已完成实际初始化推送，并用远端 main 与本地 HEAD 的一致性验证。初始化提交为 `25abb27538f6b0f47645697e684c3cebe7a8e438`。本次设计随后单独提交。

采用一个仓库管理前后端与设计。`main` 保存可以检查的里程碑，正式实施时用短期功能分支开发，例如 `feat/ui-shell`、`feat/scan-pipeline`、`feat/repair-verification`、`feat/local-assistant`。小团队不引入繁琐发布流程；每个阶段完成后检查 diff 和最小验证，合并并推送。

提交消息示例：`feat(ui): add evidence workspace`、`fix(verification): reject incomplete coverage`、`docs: record frozen evaluation results`。一次提交对应一个可解释变化；代码、锁文件与必要测试一并提交。设计稿、展示原型和真实系统分开标明，演示用模拟值不能静默进入正式数据源。

提交前检查新增文件清单及大文件，确认没有 `.env`、访问令牌、原始私有仓库、模型权重和运行快照。`.gitignore` 只是降低误提交概率，不能代替审查。私有仓库也不应提交凭据。Git 身份凭据由系统凭据管理器管理，项目配置不保存登录 token。

里程碑建议为：`design-v2-approved`、`p0-detection-ready`、`p0-verification-ready`、`demo-release`。这些标签仅在真实满足条件后建立；当前不创建“已批准”标签。

CI 后置为轻量方案：有了业务代码后，运行契约测试、Python 检查和前端构建即可，不在 CI 启动 GPU 模型或扫描用户私有目录。仓库上传能力已用实际 push 验证，不需要为每一次常规提交反复登录。

## 6. 如何呈现结果和不足

实验结果以实际输出为唯一来源。检测列出分类型 TP/FP/FN 与支持范围，修复列出适用案例、正确通过、正确拒绝、UNKNOWN 和错误通过，模型列出事实错误、引用错误、越权结论与响应时间。不能只报“成功率”并排除所有困难案例。

比较对象包括明确版本和配置的检测工具，以及我们刻意构造的“重扫无告警即算成功”简化流程。后者只是实验对照，不代表竞品都采用这种错误策略。扩展关系算法没有改善时可保留负结果，将主要贡献集中在验证契约。

在 PPT 中把数字写成“在本作品冻结的 N 个合成场景中……”，不要写“对所有真实仓库达到……”。截图中脱敏值和模拟数据清楚标注；使用预录视频时说明录制环境与版本。

## 7. 材料与答辩结构

| 页序 | 内容 | 需要展示的证据 |
|---|---|---|
| 1 | 名称与一句话价值 | 真实工作台截图 |
| 2 | 一个具体修复误判场景 | 工作区已改、index 残留的自有样例 |
| 3 | 方案范围和整体结构 | 总体架构图，P0/P1 标注 |
| 4 | 为什么不是再做一个扫描器 | 修复义务链和证据边界 |
| 5—7 | 演示闭环 | 发现、差异、验证、剩余风险 |
| 8 | 轻量模型的作用 | 引用证据解释、无模型回退 |
| 9 | 实验方法与真实结果 | 冻结划分、对照、失败案例 |
| 10 | 价值与限制 | 支持场景、未覆盖能力、下一步 |

重点准备五个追问：①凭据为什么叫疑似而不叫有效？②为何副本通过、原风险仍在？③如果扫描没扫全会怎样？④大模型胡说时谁做最终判定？⑤与现有工具相比有何可验证增量？这些问题都应能从界面定位到真实证据和对应代码。

最终材料按本地赛事模板检查匿名、摘要、章节、图片、参考资料和源码要求。赛事规则与截止时间以提交前官方最新通知为准，本计划不根据旧页面推定仍可报名。
