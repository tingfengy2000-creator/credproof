# 密证 CredProof——面向 AI 工具的凭据泄露验证与受控修复系统

## 摘要

当 AI 工具从环境变量读取凭据时，源码没有硬编码密钥，也可能在异常返回、日志或辅助函数中暴露运行时真实值。密证 CredProof 面向维护自有或获授权 Python 工具的开发者与安全人员，在发现这类线索后，把受控执行证据、候选补丁、安全与业务验收以及对应对象复检材料串成一条可交付流程。固定程序先确认触发条件和泄露通道，本地模型阅读代码与脱敏观察、提出候选，程序再判断是否允许修改和是否满足必要条件。h01 展示模型补足固定启发式未覆盖的参数日志修复；h03 展示第一份“看似脱敏”补丁因真实值仍在而被拒，反馈进入后续请求后第二份补丁通过；h07 展示无实际泄露证据时原代码保持不变。冻结八例中，C-Agent 完成四个问题例的合格修复，四个正常例实际修改为 0/4，完整任务为 6/8；失败和未完成记录保留。另有一个 Twine 公开历史问题的窄组件接入，第三份候选通过七项固定条件，不并入八例分母。密证交付的不只是一份补丁，还包括能回到具体对象重新检查的依据。

关键词：运行时凭据；本地智能体；受控修复；证据反馈；材料复检

## 一页特点说明

**一句话记忆点：让 AI 提出修复，让程序决定是否接受，让开发者能够复查。**

### 为谁解决什么问题

使用者是维护自有或获授权 Python 工具、AI 工具及相关组件的开发者和安全人员。使用时刻是：凭据已经被怀疑进入异常返回、日志等禁止输出通道，需要确认问题、修复并判断补丁是否可以交付。

### 三个有证据支撑的特点

1. **证据反馈驱动候选修复。** 固定程序先执行受控触发，模型基于代码和脱敏观察提出候选；失败回执可进入后续请求。h01 支持固定启发式之外的有限增量，h03 支持一次真实反馈调整。
2. **程序实施修改授权和安全/业务联合验收。** 模型不能修改需求、裁判或原工作区；当前副本有有效证据且候选在允许范围内，才进入检查。安全通道、认证行为、成功响应、拒绝和异常条件共同决定结果。
3. **对应对象的材料交付与独立复检。** 导出原件、当前候选、规则和轨迹；复检重新读取材料并区分旧报告适用性、历史完整性和当前 PASS/FAIL/UNKNOWN。

### 已证明与待证明

已证明的是限定场景中的真实运行、候选差异、验收结果和材料复检。尚未测量人工时间节省、企业部署收益、跨机器适配或任意代码库泛化；外部 Twine 结果是一个窄组件场景，不是泛化率。

## 同一轮完整结果

`20260929t095000z-holdout8` 的 A/B/C 问题例合格修复为 **3/4、1/4、4/4**，最终对象通过为 **7/8、5/8、8/8**，完整任务为 **7/8、4/8、6/8**。三方法正常例实际修改均为 0/4。C 的 h05/h06 工具协议未完成，不能用后续独立检查的 PASS 回填任务完成数。外部 Twine 结果单列，不拼接为整体成绩。

当前范围为授权且审查过的 Python 工具、合成凭据、固定条件和既有隔离环境。模型、框架和隔离基础设施按来源披露；本项目实现受限工具、证据门槛、裁判与完成控制、对象绑定复检和展示交付。AI 辅助开发范围、成员贡献和原创声明待队伍与指导教师确认。
