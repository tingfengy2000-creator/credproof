# 源码讲解与五个关键追问

先打开 `docs/preliminary-candidate/contribution-map.md` 对齐一页结构，再按下面四处讲。不需要逐行背诵。

1. **证据门槛：** 打开 `agent_pilot/reliability.py`，搜索 `authority` 和 `submit`。可以说：“模型认为有问题只是建议。执行器核对当前代码、规则和真实禁止通道证据，才开放补丁提交。合法认证不是泄露。”
2. **补丁生成：** 同文件 `run_method`，再打开 `model_client.py` 的 `from_ollama_response`、`LocalAgentClient.run`。可以说：“模型调用结构化工具，读取反馈再提出候选。自然语言里的工具名不会被当成命令。总调用和候选预算固定，程序验收完成后主动结束。”
3. **安全与业务验收：** 打开 `judge.py` 的 `judge_trial` 与 `isolation.py` 的 `run_isolated`。可以说：“执行侧生成合成凭据，检查禁止输出通道，同时核对认证及必要业务行为。候选在隔离环境中执行，缺隔离就不能通过。”外部组件看 `external_twine.py` 的 `boundary`、`harness`，强调 Twine 保留原业务 AST，范围仅配置解析。
4. **报告绑定：** 打开 `web.py` 的 `_require_current_material`，再看 `bundle.py` 的 `recheck_bundle`。可以说：“报告只对对应对象和条件有效。复检既看材料是否齐全，也重新执行检查；不会因为旧报告写 PASS 就直接接受。”

## 1 这与扫描器或 CI 有什么区别

扫描器可做静态或动态检测，规范 CI 也能实现很多固定检查。我们的作品把运行时泄露证据、本地模型候选、程序修改门槛及材料复检组织成面向已适配工具的操作流程。h01 表明模型补充了本项目有限启发式的修复候选，不代表成熟扫描器都做不到。CI 可承载这些机制，二者并不对立。

## 2 模型解释错了或提了危险补丁怎么办

模型不能直接判定通过或越权执行。h03 曾错误解释失败原因，但程序根据真实凭据值仍在日志中拒绝候选；后续修改经动态检查通过。Twine 前两份候选违反预定修改范围，被执行侧拒绝。界面把模型分析与程序证据分开。

## 3 为什么用 Agent 而不是固定脚本

固定脚本适合已知模式，应当继续保留。Agent 可选择工具并根据执行反馈改变候选，h03 有真实过程记录；h01 有针对固定启发式未覆盖结构的有限增量。我们没有证明 Agent 在所有任务更好，也没有测量人工成本收益。无需模型时可单独查看或重新验收。

## 4 接入 Twine 是否就是支持任意开源项目

不是。这次保留真实上游配置读取组件，固定前后提交和许可证，只适配 `.pypirc` 分支及其控制台错误输出；不运行上传和外网认证。允许修改仅一类解析异常处理，七项条件属于一个外部场景。该结果说明一种窄接入可行，不是通用仓库修复。

## 5 哪些是自己实现的 复检又能证明什么

模型、框架、推理服务和隔离基础来自开源；受限工具、证据授权、任务控制、固定裁判、对象材料绑定与工作台由本项目实现，Codex 实质参与编码。复检在可信需求和验证器前提下重读材料、再次执行条件，证明该对象满足已覆盖检查；哈希不是认证，不证明所有输入或生产环境安全。AI 辅助是否符合参赛条款仍待本人确认。
