# 密证 CredProof：不用背术语的讲解页

## 300 字说明

密证给维护自己或获得授权的 Python 工具、AI 工具的开发者使用。麻烦通常发生在工具“任务完成了”，但同时把密钥写进错误信息或日志、读取了规定目录之外的文件，或者把请求发给了未授权服务。继续交付这样的工具，秘密可能被带出，问题也很难由下一位开发者复查。使用者先提供项目入口、允许读取的目录、允许访问的本地服务和必要业务测试。密证在隔离副本中运行这些条件，记录三类安全检查和业务结果；如确有泄露，允许本地模型提出候选修改，但模型不能改变规则或直接宣布通过。最后留下候选差异、新生成的安全报告和可再次运行的导出测试。缺少隔离、测试没有执行或证据不足时，结果显示未知，不伪装成通过。

## 一条最容易记住的流程

1. **工具要完成什么？** 人工在 `credproof.toml` 中写清入口、测试、允许目录、允许服务和修改范围。
2. **实际发生了什么？** 固定程序在专用副本中触发工具，分别观察凭据输出、文件访问和网络请求。
3. **候选改了什么？** 模型只能在已经确认的泄露上提出候选；没有证据就不写补丁。
4. **补丁合格吗？** 程序重新执行必要测试，检查秘密是否消失、业务行为是否保留、是否越过修改范围。
5. **以后还能查吗？** `export-tests` 把同一检查放回项目，pytest 每次重新读取当前代码；导出回归还会核对新生成的安全报告。

网页中选择“启动时授权项目”后，可先看配置范围，再点击“现场检查 · 无模型”或“导出安全测试”。这不是后台文件浏览器：项目路径只在启动参数中登记，页面不能临时传入路径、命令或网络目标。

## 人工、程序、模型各做什么

| 角色 | 实际负责 | 不负责 |
| --- | --- | --- |
| 开发者 | 提供授权、入口、允许目录/服务和必要业务要求 | 不把模型猜测直接当作安全结论 |
| 固定程序 | 复制副本、触发测试、观察输出/文件/网络、限制修改、计算 PASS/FAIL/UNKNOWN、生成报告 | 不替模型理解任意项目 |
| 本地模型 | 阅读受限代码、提出假设、选择工具、给出候选补丁 | 不改规则、测试、隔离设施或最终判决 |

## 五个关键问答

### 1. 这是不是扫描器加 CI？

有重合。扫描器和 CI 可以发现规则问题、运行测试和阻止合并。密证当前实际增加的是一条受控交接：把当前副本、触发条件、允许修改范围、安全结果、业务结果和复检材料放在同一个流程里。没有证据就不自动改，旧对象变化后也不沿用旧 PASS。没有做过所有产品的对比，不能说全面领先。

### 2. 为什么需要模型？固定规则不够吗？

固定规则覆盖到的结构可以直接处理，h03 中 A 固定流程也成功。模型只在已确认问题的候选生成上提供帮助；h01 展示它补足一个参数日志路径，h03 展示第一份候选失败后根据真实回执调整。模型不拥有批准权限，外部项目的自动修复也没有被写成稳定成功。

### 3. 如果模型改错怎么办？

程序先检查证据、修改范围、安全通道和必要业务测试。h03 第一份补丁看起来加了脱敏词，但真实值仍在日志里，所以被拒绝；h07 没有确认泄露，原文件保持不变。模型误报、程序确认和实际修改分别记录。

### 4. 页面上的“通过”能证明什么？

只证明声明的副本、规则、测试和隔离条件下本次检查通过。它不证明真实凭据已撤销、不证明任意项目安全，也不是第三方认证。导出测试会重新执行检查，并核对新生成的安全报告；缺少必要测试或隔离时显示 UNKNOWN。

### 5. 自己做了哪些，哪些来自开源或 AI？

Qwen-Agent、Qwen3-Coder、Ollama、pytest、bubblewrap 和外部工具代码是复用基础。项目自己实现配置边界、受控副本、三类观测、候选权限、联合验收、报告绑定、导出复检和展示工作台。ChatGPT/Codex 参与了方案、主要代码、调试和材料整理；成员贡献、AI 辅助范围和原创声明仍由参赛者与指导教师确认。
