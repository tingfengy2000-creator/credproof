# 价值与创新主张

## 一句话记忆点

**让 AI 提出修复，让程序决定是否接受，让开发者能够复查。**

## 作品定位

**密证 CredProof——面向 AI 工具的凭据泄露验证与受控修复系统。**

## 谁在什么时候使用

密证面向维护自有或获授权 Python 工具、AI 工具及其组件的开发者和安全人员。当工具已经出现“凭据可能进入异常返回、日志或其他不应接收秘密的输出通道”的迹象时，使用者需要把问题从线索变成可检查的修复任务：确认触发条件，理解传播路径，比较候选补丁，检查必要业务行为是否保持，并把对应材料交给同事复查。

使用者仍需提供适配入口、可信需求、允许修改范围和必要业务条件。密证不替代人工确定系统边界，也不把“模型怀疑”直接当作漏洞结论。

## 用户原来要处理的工作

1. 找到凭据在什么输入和分支下进入输出通道；
2. 区分合法的认证用途与不允许的日志、异常、返回泄露；
3. 修改代码，同时保留成功请求、拒绝请求和异常处理行为；
4. 判断一份候选补丁是否真的消除了暴露；
5. 把代码、条件、执行证据和复检入口交付给下一位复查者。

常见的扫描或人工修复可以完成其中一部分，但“补丁是否适用于这个副本、这组条件是否实际执行、旧结论能否继续沿用”仍需要被明确记录。

## 密证多做的三步

### 1. 把证据反馈带回候选修复

固定程序先用已登记的触发条件生成初始执行证据；本地模型读取代码和脱敏观察，提出假设、选择结构化工具并提交候选。候选被真实检查拒绝时，失败原因可以进入下一次模型请求。h03 中首个补丁只改了脱敏前缀，真实值仍在日志里；程序回执进入后续请求，第二个补丁改用固定安全错误信息后通过。h01 则展示模型完成了项目固定启发式未覆盖的参数日志修复。两例分别支持“候选增量”和“反馈调整”，不合并为一个更大的成功故事。

### 2. 让程序掌握修改授权和验收

模型可以提出疑点和补丁，但不能修改需求、裁判或隔离设施，也不能自行写入原工作区。执行器只在当前副本有有效泄露证据、补丁落在允许范围内时接受候选；裁判同时检查禁止输出通道、正常认证、成功响应、拒绝和服务异常。h07 中模型有疑点，但没有实际泄露证据，原代码保持不变。Twine 的前两份候选则因越过预先固定的修改轮廓被拒绝，第三份才进入七项检查。

### 3. 让交付结果对应具体对象并可复检

导出的材料绑定原件、当前候选、需求、规则和执行记录。复检重新读取这些材料并执行必要检查，分别报告旧报告是否仍适用、历史证据是否完整以及当前对象的新结果。对象或规则变化时不沿用旧绿色结论；新复检可以独立得到 PASS、FAIL 或 UNKNOWN。

## 已经证明什么

- 在冻结的 `20260929t095000z-holdout8` 合成批次中，C-Agent 对四个问题例取得 4/4 合格最终对象，四个正常例实际修改为 0/4；完整任务为 6/8，另外两例的工具协议未完成，记录保留。
- h01、h03、h07 分别提供有限修复增量、失败反馈修正和正常对象保留的可核查过程。
- Twine 配置组件的一个公开历史问题被保留原业务逻辑并受控接入；一次本地模型任务提交三份候选，前两份被修改边界拒绝，第三份通过七项条件。它是一个外部组件场景，不是泛化率评测。
- 材料导出、对象变化拒绝旧缓存复用、无模型复检和分层启动入口已经实现并有定向记录。

## 尚待证明什么

尚未测量人工时间节省、长期维护收益、企业部署效果、跨机器可用性或对任意代码库的泛化能力。当前结论限于已登记、已适配的受控 Python 工具、合成凭据、固定条件和已有隔离环境。开源框架、模型和隔离基础设施属于复用基础；本项目实现的是受限工具、证据门槛、裁判与完成控制、对象绑定复检和展示交付。

## 评委应记住的结果

密证交付的不只是一份模型生成的补丁，而是**泄露证据、候选差异、安全与业务验收、对应对象复检材料**组成的一条可复查路径。它允许已有规则和人工继续完成能完成的工作，同时把最容易被忽略的“这份补丁是否在当前对象和条件上真正验收过”显式化。
