AI 说修好了，
凭什么采纳？

功能跑通，不等于修复合格。AI 提出建议，开发者审阅；安全与业务，用实际证据核验。

密证面向会读本地文件、带凭据调用服务的 Python 工具。它在隔离环境里真正运行修改后的代码，记录文件读了哪里、请求去了哪里、凭据出现在哪里，再把技术结论、人工决定和可复查的材料交给负责合并的人。

检查一个项目 看真实案例
谁在用？
给 Python 工具做安全修改的开发者，以及决定是否合并的负责人。这类工具会读本地资料、带凭据调用服务，常由 AI 帮忙修改。
遇到了什么风险？
修改后测试变绿，工具却可能读出允许目录、跟着跳转把凭据带到别处、把凭据写进日志；也可能什么都没做，所以“看起来安全”。
比普通测试报告多什么？
实际运行时的行为证据：读了哪些文件、请求去了哪里、凭据出现在哪里，以及必要的业务行为是否真的发生。
最后拿到什么？
一份绑定到确切代码的验收报告和独立的人工决定，加上一个别人能在新目录重做检查的导出包。

一个真实案例：资料助手

资料助手是一个小型 Python 工具：按请求读取一份资料，再带着凭据调用一个服务。实验只使用每次随机生成的合成凭据和本机模拟服务。下面六步全部来自已保存的真实记录；你也可以在“新建检查”里选择这个示例，自己走一遍。

第 1 步

原问题：三条风险路径

原版 tool.py 是实验室里故意留下漏洞的示例。业务测试 4 项中能通过 2 项，看上去“基本能用”。

  • 1路径不设限：按请求给的路径直接打开文件，检查中实际读到了 secrets/secret.txt。
  • 2跟随跳转：允许服务返回 302 后，urlopen 自动跟到禁止服务 /secret，认证头一起带过去。
  • 3凭据外流：凭据写进日志，又作为返回值交出去；标准输出里也能看到。

依据：原版完整检查报告，判定 FAIL，7 项必要条件未满足。

第 2 步

AI 候选：方向对了，但漏了东西

这是本地模型给出的历史候选，演示中原样导入为 v000，没有重新推理。

做对的部分

读文件和调服务改成了固定访问组件 read_text 与 get_json，日志和返回值里也不再放凭据。三条风险路径的修改方向都对。

遗漏的部分

  • a删掉了 import os：模型说要补 urllib.error 的导入，实际却删除了 os 的导入，第 17 行一运行就报 NameError。
  • b异常转换不对：引用了没有导入的 urllib，并把跳转产生的 HTTPError 改成 ValueError，与“遇到跳转应抛出 HTTPError、不跟随”的要求冲突。
  • c残留无用导入：json、Request、urlopen 都已不再使用。

只找违规的检查，在这一版上什么也找不到：没有越界、没有禁止请求、没有泄露。

密证仍判 FAIL，理由是应该发生的事没有发生：资料没读、服务没认证、必要测试 3 项失败。

第 5 步

技术通过，仍待人工采纳

v001 的检查通过了，但这只是三个状态中的一个。页面把它们分开显示，任何一个都不会替另一个做决定。

  • FAIL 的版本不能被批准：对 v000 提交批准，服务端返回 409。
  • 批准后再次运行检查，结果仍是 PASS，但批准不会自动恢复，需要重新决定。
  • 每次决定追加保存，历史保留；本机记录不是强身份签名。

第 6 步

导出复检：材料移走后，别人能不能重做？

导出的是同一个对象：代码、配置、必要测试、访问组件和报告摘要。复检方重新执行完整检查，得到新的运行证据，而不是信任一份保存的“通过”。导出不会自动把代码应用到原项目。

  1. 导出同一对象代码、配置、必要测试、访问组件和报告摘要一起导出。导出不应用代码，收据追加保存
  2. 匿名取件不带账号凭据，从固定提交逐字节取回公开包并核对清单。17 个文件全部一致
  3. 新目录完整复检在新目录用原检查器重新运行，生成新的报告。复检完成，原报告仍然适用
  4. 导出的回归测试用普通 pytest 检验导出测试能否发现缺陷。修复版 0 项失败；重新引入缺陷 1 项失败；无关改动 0 项失败

在工作台里，“复检导出包”页面可以直接上传导出的 zip，在新目录重新执行完整检查。命令退出码为 0 不等于 PASS，要读新报告里的判定、逐项测试和场景完成情况。

两个贡献

目前主要是工程与场景创新，不是已经建立强算法壁垒的项目。

贡献一

不只看有没有出事，还检查该做的事是否真正发生

同一个 v000，两种看法
只看有没有出事还看该做的做了没有
越界读取 0 次允许资料读取 0 次
禁止服务回执 0 次带凭据的认证请求 0 次
凭据泄露 0 处必要测试 4 项只过 1 项
看起来安全FAIL：修复不合格

适用范围：结论只在已实现、已验证的观察范围内有效，包括 Python 审计钩子、模拟服务回执、输出与日志捕获和隔离运行。报告会列出未覆盖项，不能推广成任意 Python 执行的完整安全证明。

贡献二

技术结果与人工采纳分开，并对应同一份修改

批准的是哪份代码？
决定绑定代码摘要、项目树摘要和报告摘要，提交时三者都要核对。
依据哪些检查？
绑定那一份报告：14 项必要条件、逐项测试结果，以及冻结的配置与测试。
配置或组件变化后，旧批准还算不算数？
不算。结论回到 UNKNOWN、决定回到待定，旧页面的提交返回 409；重新检查也不会自动恢复批准。
材料移走后，别人能不能重做检查？
能。导出包可以在新目录重新执行完整检查，产生新的运行证据。

常见质疑

为什么不用现有 CI 或安全扫描器？

现有工具擅长的事我们照用：业务测试仍由 pytest 运行，检查结果也能以 SARIF 和 JUnit 交给现有 CI 和代码扫描界面。

区别在观察对象。静态扫描读的是代码文本，CI 看的是测试是否通过；密证在隔离环境里实际运行修改后的代码，记录文件访问、请求去向、服务回执和凭据出现的通道，并要求必要行为确实发生。最后交付的是别人能重做的检查，而不是一句“通过”。

最后还是人工改代码，AI 有什么作用？

在这个案例里，AI 给出了真实的候选：改用固定访问组件，方向正确；但删掉了 os 的导入，也转错了异常。开发者在 Codex 辅助下，对照这份候选和它的差异完成修订，再交给检查器独立验收。

我们没有证明模型能独立修复，也没有测量节省了多少时间。产品的主要价值不依赖 AI 每次都成功：AI 的候选错了，检查器同样会拦下。

这不就是 CI 加审批吗？

规范的 CI 确实能实现其中一部分，甚至相同的判定。我们不是发明 CI，而是针对 Python 工具的安全修改，提供现成的行为观察、验收条件、对象绑定和复检流程。

目标是减少每个项目从零组织这些能力的工作。这是产品目标，目前还不是测量过的收益。

                      AI 只能提出补丁，程序决定是否通过，人决定是否采纳。
                      
          
                      三种权力分开：AI 看不到真实凭据，也不能修改测试和规则；程序的判定人不能推翻；采纳决定绑定到确切的代码版本，代码一变就失效。
                      
        
                      
        
                        
          
                      1. 确认问题在隔离副本中运行原始代码，取得真实违规证据后才开放修复。
                        2. 
          
                      2. AI 提出补丁本地模型只读取允许的代码和脱敏证据，只能修改登记的入口文件。
                        3. 
          
                      3. 程序验收补丁进入新的隔离副本，重新运行全部业务测试和安全场景，按 14 项条件判定。
                        4. 
          
                      4. 开发者修订AI 修不好时，开发者提交新版本，同样要重新验收。
                        5. 
          
                      5. 人工采纳只有当前完整通过的版本才能采纳；重新验收后旧批准不会自动恢复。
                        6. 
          
                      6. 导出与复检导出补丁、规则、依赖和报告，在任何新目录都能重新执行完整验收，而不是读取保存的结论。

                      三种结论
                      
          
                      
            
                      通过
                      本配置声明的 14 项条件全部满足：没有泄密、没有越界，业务测试全部通过；配置要求时，还必须实际读取允许的资料、实际带凭据访问允许的服务。
                      
            
                      不通过
                      至少有一项明确反例，例如凭据出现在日志里，或禁止的服务收到了请求。一刀切地拒绝所有访问同样不通过。
                      
            
                      证据不足
                      隔离环境不可用、必要测试被跳过，或者需要网络的场景在发出请求前就报错。提前报错不能当作安全。
